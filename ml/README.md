# ClassVault ML pipeline

Trains the **academic risk** and **SGPA forecast** models the app uses for
decision support. Training happens here in Python; the app imports the
resulting model files and runs predictions itself (offline, on every platform).

Predictions are signals for faculty review. They are never shown to students
and never make decisions.

## Workflow

1. **Export** – in the app, *Prediction Models → Export CSV* (admin). One row
   per student per semester; students appear only as one-way hashed keys.
2. **Train**
   ```sh
   cd ml
   python -m pip install -r requirements.txt
   python -m classvault_ml train path/to/classvault_training_fv1_YYYYMMDD.csv --out models
   ```
   Writes `risk-….json`, `forecast-….json` and `report-….md`.
3. **Import & activate** – *Prediction Models → Import Model Files*, review the
   evaluation, activate one model per task.
4. **Predict** – *Academic Insights → Generate Predictions* for a section.

## What the pipeline does

| Step | Detail |
|---|---|
| Features | Defined once in `feature_spec.json` and computed by the app (`lib/features/prediction/engine/feature_extractor.dart`) for both export and live prediction. A test fails if the two lists diverge. |
| Leakage | A row for semester *T* uses only semesters before *T*. Backlog features count first-attempt failures only, because re-attempt dates are unknown. |
| Labels (`labels-v1`) | Risk = any first-attempt failure in *T*, SGPA(*T*) < 6.0, or a drop of 1.0+ from *T-1*. Forecast = SGPA(*T*). |
| Split | 60/20/20 train/validation/test **by student**, so no student is in two parts. |
| Missing data | Median imputation + missing indicators, fitted on training rows only. |
| Models | Logistic regression vs gradient-boosted trees (risk); ridge vs gradient-boosted trees (forecast). Trees must beat the linear model by a margin to be chosen. |
| Calibration | Platt scaling on validation rows; "elevated" threshold maximises F1 on validation; "moderate" starts at the base rate. |
| Ranges | Split-conformal 80% intervals from validation residuals. |
| Evaluation | Held-out test students: AUC, average precision, Brier, calibration table, precision/recall, per-semester stability; MAE/RMSE and interval coverage. Compared against simple baselines. |
| Stability | The chosen model family is refitted on 5 student-grouped folds of the training and validation rows (test rows untouched). The report shows the spread; a model whose quality depends on the split fails *Stable across data splits*. |
| Checks | A model is only *recommended* if it beats the baselines, is calibrated, is stable across splits and (for forecasts) its interval covers close to 80%. Synthetic data is never recommended. The app asks for explicit acknowledgement before activating a model with warnings. |

Refuses to train with fewer than 200 rows, 50 students or 30 outcomes per class
(`--allow-small` overrides, for experiments only).

## Explanations

Every prediction stores its feature values, the model and feature versions,
the baseline (expected output for a typical training student) and each
feature's contribution. In the app, *Why this signal?* shows these, the model
card, suggested next steps, and whether the student's data has changed since.

| Model | Method |
|---|---|
| Logistic / ridge | coefficient × standardised value: the exact SHAP value relative to the training average (features treated as independent) |
| Gradient-boosted trees | exact path-dependent TreeSHAP, computed in the app by enumerating each tree's feature subsets; checked against the `shap` library to 1e-6 |
| Trees from files without `cover` | decision-path attribution, labelled *approximate* |

Contributions for risk are in log-odds; for the forecast in SGPA points. They
always add up exactly to the prediction.

Models that have made predictions cannot be removed from the app, only
deactivated, so every stored prediction stays traceable to its model.

## Pilot

Before relying on predictions, run the pilot described in `docs/pilot-plan.md`. After the pilot semester's
results are imported, *Admin → Pilot Evaluation* compares every prediction with what actually happened.

## Synthetic data

`tests/data/synthetic_fv1.csv` is generated by the app's real feature extractor
from fictional histories (`SyntheticHistoryGenerator`), so the pipeline can be
tested before real data exists. Training on it needs `--allow-synthetic`, and
the resulting models are labelled **SYNTHETIC: TEST ONLY** everywhere in the app.

Regenerate it with:

```sh
CLASSVAULT_WRITE_SYNTHETIC=ml/tests/data/synthetic_fv1.csv flutter test test/feature_extractor_test.dart
```

## Tests

```sh
cd ml
python -m pip install -r requirements-dev.txt   # adds shap, used only to check explanations
python -m unittest discover -s tests -v
```

Without `shap`, the explanation check is skipped and the parity fixture has no
SHAP reference values (the app's parity test will then say to regenerate it).

The app side checks it reproduces scikit-learn exactly (`test/model_parity_test.dart`,
using `test/fixtures/ml_parity.json`). Regenerate the fixture after changing the
model format:

```sh
cd ml && python -m classvault_ml train tests/data/synthetic_fv1.csv --out ../build/ml-try \
  --allow-synthetic --parity-fixture ../test/fixtures/ml_parity.json
```

## Changing features

Edit `feature_spec.json` **and** `FeatureSpec` / `FeatureExtractor` in the app
together, bump `featureVersion`, re-export and retrain. The app rejects model
files built for a different feature version.
